1. Mục tiêu học tập

Sau bài học, người học có thể phân biệt data, database, DBMS, RDBMS; giải thích vì sao DBMS cần thiết; nhận diện các thành phần chính; và có bức tranh tổng thể về SQL, transaction, index, normalization, security và recovery.

Khái niệm

Data → Information → Database → DBMS.

Kiến trúc

User/Application → DBMS → Storage.

Mô hình dữ liệu

Relational, document, key–value, graph, time-series…

Nền tảng học tiếp

SQL, keys, ACID, concurrency, indexing và normalization.

2. Data và Information

Data là các biểu diễn có thể lưu trữ và xử lý: số, chữ, ngày tháng, ảnh, âm thanh, tọa độ, log, dữ liệu cảm biến… Information là dữ liệu đã được đặt trong ngữ cảnh và xử lý để trở nên có ý nghĩa.

Data + Context + Processing → Information → Decision
Ví dụ: 41,800 chỉ là dữ liệu. “Giá cổ phiếu là 41.800 VND tại 10:30” có ngữ cảnh. “Giá hiện tại cao hơn giá vốn 6,2%” là thông tin phục vụ phân tích.

3. Database là gì?

Database (cơ sở dữ liệu) là một tập dữ liệu có tổ chức, được thiết kế để lưu trữ, truy xuất và cập nhật hiệu quả.

Hệ thốngDữ liệuTruy vấn điển hình
Đại họcSinh viên, môn học, lớp, đăng kýSV nào đang học DBMS?
E-commerceKhách, sản phẩm, đơn hàngDoanh thu hôm nay?
LogisticsĐơn hàng, xe, tuyến, khoĐơn nào đang trễ?
Ngân hàngTài khoản, giao dịchSố dư hiện tại?
Không nên đồng nhất database với một bảng Excel lớn. Database thường phải hỗ trợ schema, nhiều người dùng, truy vấn, ràng buộc, giao dịch, bảo mật và phục hồi.

4. DBMS là gì?

Database Management System (DBMS) là phần mềm cho phép định nghĩa, tạo, duy trì và thao tác database. DBMS là lớp trung gian giữa users/applications và dữ liệu.

Cách nhớ: Database = dữ liệu có tổ chức. DBMS = phần mềm quản lý dữ liệu đó.

6. File System vs DBMS

Nếu mỗi ứng dụng tự lưu dữ liệu trong các file riêng, hệ thống dễ gặp redundancy, inconsistency, khó truy vấn, khó đồng bộ ghi, khó kiểm soát quyền và khó recovery.

Vấn đềFile-basedDBMS
RedundancyDễ sao chép dữ liệuSchema giúp kiểm soát duplication
ConsistencyDễ lệch giữa nhiều fileConstraints + transactions
QueryTự viết code đọc/searchQuery language + optimizer
ConcurrencyKhó xử lý ghi đồng thờiConcurrency control
SecurityThường ở mức fileUser/role/privilege
RecoveryỨng dụng tự xử lýLogging + backup + recovery

8. Kiến trúc ba mức

Một cách nhìn kinh điển chia database thành External – Conceptual – Internal.

Data independence nhằm giảm tác động của thay đổi ở tầng thấp lên tầng cao. Ví dụ, thêm một index vật lý không nên buộc ứng dụng đổi business logic.

9. Schema, Instance và Metadata

Schema

Mô tả cấu trúc tương đối ổn định của database.

Instance / State

Dữ liệu thực tế tại một thời điểm.

CREATE TABLE Student (
  StudentID INT PRIMARY KEY,
  FullName  VARCHAR(100),
  Major     VARCHAR(50)
);

Metadata là “data about data”: table names, columns, types, indexes, constraints, privileges… được lưu trong catalog/data dictionary.

10. Các Data Models

Data model quy định cách dữ liệu được cấu trúc, liên hệ và thao tác ở mức logic/khái niệm. Để sinh viên dễ phân biệt, dưới đây là bảng so sánh nhanh và các hình minh họa trực quan cho từng mô hình.

ModelCấu trúcĐặc trưng
RelationalTablesRows, columns, keys, SQL
HierarchicalTreeParent–child
NetworkRecords + linksQuan hệ dạng mạng, một nút có thể có nhiều liên kết
Object-orientedObjectsObject identity, attributes, methods, inheritance
DocumentJSON/BSON-like documentsNested, flexible structure
Key–valueKey → valueTruy cập trực tiếp theo key
GraphNodes + edgesTraversal và quan hệ phức tạp
Không có một data model tốt nhất cho mọi bài toán. Lựa chọn phụ thuộc workload, consistency, scalability, latency và khả năng vận hành. Tuy nhiên, nhìn đúng hình dạng tự nhiên của dữ liệu sẽ giúp chọn đúng mô hình hơn.

Graph model đặc biệt hữu ích khi trọng tâm là mạng quan hệ, ví dụ: social network, recommendation, fraud detection, route planning, citation network.

Tốt khi dữ liệu có cấu trúc rõ, nhiều ràng buộc và nhiều phép join.

Graph

12. NoSQL

NoSQL là nhãn rộng cho nhiều họ database không lấy relational table truyền thống làm mô hình chính.

Document

{"id":1001,"name":"An","phones":["090..."]}

MongoDB, Couchbase.

Key–Value

session:abc → {"user":1001}

Redis, DynamoDB.

Column-family

Hướng tới dữ liệu phân tán và throughput lớn.

Graph

Nodes/edges cho mạng quan hệ sâu.

NoSQL không có nghĩa là “không có schema” hoặc “luôn nhanh hơn SQL”.

15. Keys và Constraints

CREATE TABLE Department (
  DepartmentID INT PRIMARY KEY,
  Name VARCHAR(100) UNIQUE NOT NULL
);

CREATE TABLE Employee (
  EmployeeID INT PRIMARY KEY,
  FullName VARCHAR(100) NOT NULL,
  Salary DECIMAL(12,2) CHECK (Salary >= 0),
  DepartmentID INT,
  FOREIGN KEY (DepartmentID)
    REFERENCES Department(DepartmentID)
);

16. Transaction và ACID

Transaction là một đơn vị công việc logic cần được xử lý như một khối nhất quán.

BEGIN;
UPDATE Account SET Balance = Balance - 1000000 WHERE AccountID='A';
UPDATE Account SET Balance = Balance + 1000000 WHERE AccountID='B';
COMMIT;

Atomicity

All-or-nothing.

Consistency

Giữ các invariant/ràng buộc hợp lệ.

Isolation

Kiểm soát tương tác giữa transaction đồng thời.

Durability

Sau commit, kết quả phải bền vững theo cam kết hệ thống.

17. Concurrency Control

Khi nhiều transaction cùng đọc/ghi, interleaving không phù hợp có thể gây lost update hoặc các hiện tượng đọc không mong muốn.

Thời điểmT1T2
1Read stock=10
2Read stock=10
3Sell 1 → write 9
4Sell 2 → write 8

DBMS có thể dùng locking, timestamp/versioning, MVCC và isolation levels để điều phối.

18. Index

Index là cấu trúc dữ liệu bổ sung giúp DBMS tìm row nhanh hơn cho một số workload, đổi lại tốn storage và chi phí bảo trì khi ghi.

Lợi ích

Giảm lượng dữ liệu phải scan cho predicates, joins, ranges hoặc ordering phù hợp.

Chi phí

Tốn disk/RAM; INSERT/UPDATE/DELETE có thể phải cập nhật index.

Không tạo index cho mọi cột. Index design phải dựa trên truy vấn thực tế và execution plans.

19. Normalization

Normalization tổ chức relational schema nhằm giảm redundancy có hại và insert/update/delete anomalies dựa trên dependencies của dữ liệu.

StudentIDStudentNameCourseIDCourseNameLecturer
S01AnC01DBMSDr. Minh
S02BinhC01DBMSDr. Minh

CourseName và Lecturer bị lặp. Có thể tách:

STUDENT(StudentID, StudentName)
COURSE(CourseID, CourseName, Lecturer)
ENROLLMENT(StudentID, CourseID)

20. Security, Integrity và Recovery

Authentication

Xác minh user/service.

Authorization

Ai được SELECT/INSERT/UPDATE/DELETE?

Integrity

PK, FK, UNIQUE, CHECK, NOT NULL.

Audit

Theo dõi thao tác quan trọng.

Backup

Tạo bản sao có thể phục hồi.

Recovery

Khôi phục sau crash/lỗi/thao tác sai.

Least privilege: user/service chỉ nên có quyền tối thiểu cần thiết.
Backup chưa kiểm thử restore chưa đủ. Cần quy trình recovery và mục tiêu RPO/RTO phù hợp.

21. Ứng dụng kết nối Database

Các cơ chế phổ biến: native drivers/connectors, JDBC/ODBC, ORM và ODM.

ORM không thay thế kiến thức database. Schema, index, transaction và query patterns vẫn quyết định tính đúng và hiệu năng.

22. Chọn Database thế nào?

Không nên bắt đầu bằng “database nào nhanh nhất?”. Hãy bắt đầu bằng workload.

Câu hỏiCần phân tích
Dữ liệu?Tabular, nested document, graph, time-series?
Query?Point lookup, joins, traversal, aggregation?
Consistency?Giao dịch tài chính hay cache/session?
Read/write?Read-heavy, write-heavy, append-only?
Scale?Volume, request rate, geographic distribution?
Availability?Replication/failover, downtime?
Team?Expertise và toolchain?
Ví dụ: hệ thống đăng ký học phần có transactions, constraints và nhiều relationships → relational DB là điểm khởi đầu tự nhiên; social graph có truy vấn nhiều hop → cân nhắc graph DB; sensor telemetry → cân nhắc time-series storage.

23. Ví dụ xuyên suốt: Đăng ký học phần

STUDENT —< ENROLLMENT >— SECTION —> COURSE
STUDENT(StudentID PK, FullName, Email UNIQUE)
COURSE(CourseID PK, CourseName, Credits)
SECTION(SectionID PK, CourseID FK, Semester, Capacity)
ENROLLMENT(StudentID PK/FK, SectionID PK/FK, EnrollDate, FinalGrade)
SELECT s.StudentID, s.FullName, e.FinalGrade
FROM Student s
JOIN Enrollment e ON e.StudentID = s.StudentID
WHERE e.SectionID = 202601;

Một ví dụ duy nhất có thể nối toàn bộ môn: ER model → relational model → SQL → constraints → normalization → transaction → indexing → authorization.

24. Lộ trình học DBMS

  1. Foundations: data, database, DBMS, architecture.
  2. ER/EER Modeling: entity, relationship, cardinality, specialization.
  3. Relational Model: relations, tuples, domains, keys.
  4. ER → Relational Mapping.
  5. SQL: DDL, CRUD, joins, aggregation, subqueries, views.
  6. Relational Algebra.
  7. Functional Dependencies.
  8. Normalization: 1NF → 3NF/BCNF.
  9. Storage & Indexing: files, B/B+ trees, hashing.
  10. Transactions: ACID, schedules, serializability.
  11. Concurrency & Recovery.
  12. Security & Administration.
  13. NoSQL / Distributed / Warehousing.
Model correctly → Query correctly → Store efficiently → Execute safely → Operate reliably

25. Ngộ nhận thường gặp

Database = Excel

DBMS còn có transactions, concurrency, query engine, constraints, privileges…

MySQL = SQL

MySQL là DBMS; SQL là ngôn ngữ.

NoSQL = không schema

Dữ liệu vẫn có structure và invariants.

Index luôn tốt

Index có trade-off read/write/storage.

Cloud DB là data model

Cloud là môi trường cung cấp/triển khai.

ORM thay thế SQL

ORM chỉ là abstraction phía ứng dụng.
