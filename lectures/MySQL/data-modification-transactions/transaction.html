1. Bản chất Transaction & Mô hình ACID trong RDBMS

Một Transaction (Giao dịch CSDL) là một đơn vị công việc logic bao gồm một hoặc nhiều thao tác SQL, đảm bảo tính toàn vẹn ngay cả khi mất điện hoặc lỗi phần mềm.

Khái niệm Đơn vị công việc logic (Unit of Work)

Xét nghiệp vụ chuyển 500.000 VNĐ từ tài khoản A sang tài khoản B:

  1. Kiểm tra số dư tài khoản A có đủ không.
  2. Trừ 500.000 VNĐ ở tài khoản A (UPDATE bank_accounts SET balance = balance - 500000 WHERE id = A).
  3. Cộng 500.000 VNĐ ở tài khoản B (UPDATE bank_accounts SET balance = balance + 500000 WHERE id = B).
  4. Ghi sổ nhật ký giao dịch vào bảng audit_log.
Quy tắc sinh tử: Cả 4 bước trên phải thành công toàn bộ, hoặc nếu máy chủ sập nguồn ở bước 2 thì bước 2 phải được hoàn tác hoàn toàn (Rollback). Không thể có trạng thái tiền đã mất ở A mà B chưa nhận được!

Storage Engine InnoDB vs MyISAM trong MySQL

Đặc tính InnoDB (Khuyên dùng) MyISAM (Cũ)
Hỗ trợ Transaction Có (ACID đầy đủ) Không hỗ trợ
Khả năng ROLLBACK Hoàn tác an toàn qua Undo Log Không thể hoàn tác
Cấp độ Khóa (Locking) Khóa mức dòng (Row-level Locking) Khóa toàn bảng (Table-level)
Bảo vệ mất điện (Crash Recovery) Redo Log & WAL (Tự phục hồi) Dễ hỏng bảng (Corrupted)

Bốn Trụ cột ACID của Giao dịch CSDL

A - Atomicity

Tính Nguyên tử

"Tất cả hoặc không gì cả" (All-or-Nothing). Hoặc toàn bộ câu lệnh đều thành công và ghi nhận vĩnh viễn, hoặc khi xảy ra sự cố, tất cả thay đổi sẽ bị xóa sạch như chưa từng xảy ra nhờ Undo Log.

C - Consistency

Tính Nhất quán

Chuyển CSDL từ trạng thái hợp lệ này sang trạng thái hợp lệ khác. Không bao giờ vi phạm ràng buộc toàn vẹn (PRIMARY KEY, FOREIGN KEY, CHECK số dư không âm, UNIQUE).

I - Isolation

Tính Cô lập

Các giao dịch chạy đồng thời độc lập với nhau, không nhìn thấy dữ liệu chưa commit của nhau. Được quản lý qua Khóa (Locking) và MVCC (Multi-Version Concurrency Control).

D - Durability

Tính Bền vững

Khi lệnh COMMIT đã phản hồi thành công, dữ liệu được ghi nhận vĩnh viễn vào đĩa (thông qua Redo Log & WAL). Ngay cả khi mất điện đột ngột 1 mili-giây sau đó, dữ liệu vẫn không bị mất.

2. Vòng đời Trạng thái & Bộ câu lệnh Kiểm soát Transaction

Nắm vững quy trình chuyển đổi trạng thái và cách sử dụng SAVEPOINT để hoàn tác từng phần.

Sơ đồ Chuyển dịch Trạng thái Transaction

Active: Đang thực thi các câu lệnh DML. Partially Committed: Câu lệnh cuối cùng đã chạy, chuẩn bị ghi đĩa. Committed: Ghi nhận vĩnh viễn. Failed / Aborted: Gặp lỗi cú pháp, vi phạm khóa hoặc có lệnh ROLLBACK.

Bộ 6 Lệnh Kiểm soát Transaction

-- 1. Bắt đầu transaction tường minh
START TRANSACTION;  -- hoặc BEGIN;

-- 2. Đặt điểm lưu an toàn
SAVEPOINT sp_step1;

-- 3. Hoàn tác một phần về điểm lưu (transaction VẪN ĐANG ACTIVE!)
ROLLBACK TO SAVEPOINT sp_step1;

-- 4. Hủy điểm lưu (không hoàn tác, chỉ giải phóng bộ nhớ)
RELEASE SAVEPOINT sp_step1;

-- 5. Xác nhận toàn bộ thay đổi vĩnh viễn
COMMIT;

-- 6. Hoàn tác toàn bộ thay đổi từ đầu transaction
ROLLBACK;
Lưu ý về Autocommit: Theo mặc định trong MySQL, biến @@autocommit = 1. Mỗi câu lệnh đơn lẻ được tự động commit ngay lập tức! Muốn gộp nhiều lệnh, ta bắt buộc phải dùng START TRANSACTION hoặc đặt SET autocommit = 0;.

3. Bẫy Tử Thần: Implicit Commit (Tự động Commit ngầm)

Một trong những lỗi phổ biến nhất của lập trình viên và quản trị viên CSDL MySQL là gọi lệnh DDL bên trong Transaction.

Hiện tượng xảy ra khi chạy DDL

Trong MySQL, hầu hết các câu lệnh DDL (Data Definition Language) và quản trị không thể rollback được. Khi bạn đang mở một transaction và gọi một câu lệnh DDL, MySQL sẽ ngay lập tức thực hiện một lệnh COMMIT ngầm định (Implicit Commit) cho tất cả các thao tác trước đó trước khi chạy câu DDL!

Ví dụ nguy hiểm: 
START TRANSACTION;
UPDATE bank_accounts SET balance = 0; -- Trừ sạch tiền!

-- Vô tình chạy 1 lệnh DDL:
CREATE TABLE temp_test (id INT); -- 💥 KÍCH HOẠT IMPLICIT COMMIT!

ROLLBACK; -- ❌ VÔ HIỆU! Lệnh UPDATE bên trên ĐÃ BỊ LƯU VĨNH VIỄN!

Bảng phân loại Lệnh An toàn vs Lệnh gây Implicit Commit

Loại lệnh Ví dụ câu lệnh Khả năng Rollback
DML (An toàn) INSERT, UPDATE, DELETE, SELECT Hoàn tác an toàn 100%
DDL Table CREATE TABLE, ALTER TABLE, DROP TABLE, RENAME TABLE Gây Implicit Commit
Dọn dẹp nhanh TRUNCATE TABLE (DDL, không kích hoạt trigger) Gây Implicit Commit
Quản trị Schema CREATE DATABASE, DROP DATABASE Gây Implicit Commit
Khóa & Transaction LOCK TABLES, UNLOCK TABLES, START TRANSACTION (khi đang có tx mở) Gây Implicit Commit

4. Mức độ Cô lập (Transaction Isolation Levels) & Các hiện tượng Concurrency

Khi nhiều session đồng thời thao tác trên cùng bảng dữ liệu, chuẩn SQL định nghĩa 4 mức cô lập để cân bằng giữa Tốc độ và Tính an toàn.

Mức cô lập (Isolation Level) Dirty Read (Đọc rác) Non-Repeatable Read (Đọc không lặp lại) Phantom Read (Bóng ma) Ghi chú & Ứng dụng
READ UNCOMMITTED Có thể bị Có thể bị Có thể bị Thấy cả dữ liệu chưa commit của transaction khác. Tốc độ cao nhất nhưng nguy hiểm nhất.
READ COMMITTED Ngăn chặn Có thể bị Có thể bị Chỉ đọc dữ liệu đã commit. Mức mặc định của Oracle, PostgreSQL, SQL Server.
REPEATABLE READ Ngăn chặn Ngăn chặn Ngăn chặn (InnoDB Next-Key Locks) MẶC ĐỊNH CỦA MYSQL INNODB. Đảm bảo mọi lần SELECT trong cùng tx đều thấy dữ liệu như nhau.
SERIALIZABLE Ngăn chặn Ngăn chặn Ngăn chặn Cô lập tuần tự tuyệt đối (chuyển các câu SELECT thuần thành khóa chia sẻ S-Lock). Hiệu năng thấp nhất.
Cú pháp thiết lập mức cô lập trong MySQL: SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED; hoặc kiểm tra bằng: SELECT @@transaction_isolation;.
