1. Data Type là gì?

Data type quy định loại giá trị một column có thể lưu, cách DBMS biểu diễn giá trị đó và những phép toán nào có ý nghĩa.

Integrity

Ngăn lưu “abc” vào cột số hoặc ngày tháng sai loại.

Storage

Kiểu nhỏ hơn có thể dùng ít dung lượng hơn.

Performance

Ảnh hưởng index, sorting, comparison và calculation.

Semantics

Schema thể hiện đúng ý nghĩa: ngày là DATE, tiền là DECIMAL.

Business meaning → Domain of values → Data type → Constraints
Ví dụ: “Giá sản phẩm” không chỉ là một con số. Nó cần số thập phân chính xác, không âm và có đơn vị tiền tệ. Vì vậy DECIMAL(12,2) CHECK(price >= 0) thường phù hợp hơn FLOAT.

3. Integer Types trong MySQL

Integer types lưu số nguyên chính xác. MySQL có nhiều kích thước để cân bằng range và storage.

TypeBytesSigned RangeUnsigned Range
TINYINT1-128 … 1270 … 255
SMALLINT2-32,768 … 32,7670 … 65,535
MEDIUMINT3-8,388,608 … 8,388,6070 … 16,777,215
INT4-2,147,483,648 … 2,147,483,6470 … 4,294,967,295
BIGINT8-263 … 263-10 … 264-1

Ví dụ

CREATE TABLE inventory (
    product_id BIGINT PRIMARY KEY,
    stock      INT NOT NULL,
    rating     TINYINT
);
Chọn type nhỏ nhất nhưng vẫn bao phủ được miền giá trị hợp lý trong tương lai. Không cần BIGINT cho mọi cột số nguyên.

Thực hành Integer

Chọn type cho: (a) tuổi người 0–120, (b) số lượng sản phẩm có thể đến 100,000, (c) ID của bảng có thể có hàng tỷ rows.

Gợi ý

(a) TINYINT UNSIGNED; (b) ít nhất MEDIUMINT UNSIGNED trong MySQL; (c) thường BIGINT.

4. SIGNED và UNSIGNED

Integer types MySQL mặc định là signed. UNSIGNED bỏ miền âm để tăng miền dương.

stock INT UNSIGNED NOT NULL
age   TINYINT UNSIGNED

Dùng hợp lý

Count, stock, age, identifier không có ý nghĩa âm.

Không chỉ dựa vào type

Nếu business rule cần giới hạn hẹp hơn, thêm CHECK.

age TINYINT UNSIGNED
    CHECK (age BETWEEN 0 AND 120)
`UNSIGNED` là đặc trưng MySQL, không phải cú pháp portable giữa mọi DBMS.

5. DECIMAL / NUMERIC — Exact Fixed-Point

DECIMAL(p,s) phù hợp khi cần biểu diễn số thập phân chính xác.

p = precision = tổng số chữ số
s = scale = số chữ số sau dấu thập phân

Ví dụ DECIMAL(10,2)

Có tối đa 10 chữ số, trong đó 2 chữ số sau dấu thập phân.

CREATE TABLE product (
    product_id INT PRIMARY KEY,
    price DECIMAL(12,2) NOT NULL,
    tax_rate DECIMAL(5,4)
);

Tại sao dùng DECIMAL cho tiền?

Vì tiền thường yêu cầu arithmetic chính xác theo hệ thập phân. FLOAT/DOUBLE dùng biểu diễn floating-point nhị phân nên có thể xuất hiện sai số xấp xỉ.

Thực hành DECIMAL

Chọn type cho: lương tối đa 99,999,999.99 và tỷ lệ lãi suất cần lưu tới 4 chữ số sau dấu phẩy.

Gợi ý
salary DECIMAL(10,2)
interest_rate DECIMAL(7,4)

6. FLOAT và DOUBLE — Approximate Numeric

FLOAT và DOUBLE dành cho số thực xấp xỉ, đặc biệt trong đo lường, mô phỏng hoặc tính toán khoa học.

FLOAT

Độ chính xác thấp hơn, storage nhỏ hơn trong các triển khai thông thường.

DOUBLE

Độ chính xác lớn hơn FLOAT.

CREATE TABLE sensor_reading (
    sensor_id INT,
    temperature DOUBLE,
    humidity DOUBLE
);
Không dùng FLOAT/DOUBLE làm mặc định cho tiền. Ví dụ phép cộng thập phân có thể không biểu diễn chính xác tuyệt đối trong floating point.

Thực hành Exact vs Approximate

Chọn DECIMAL hay DOUBLE cho: (a) giá cổ phiếu cần tính tiền, (b) tọa độ/đo đạc khoa học, (c) số tiền hóa đơn.

Gợi ý

(a) DECIMAL; (b) DOUBLE; (c) DECIMAL.

Ví dụCountryCode CHAR(2)FullName VARCHAR(100)
 
CREATE TABLE customer (
    customer_id BIGINT PRIMARY KEY,
    country_code CHAR(2),
    full_name VARCHAR(100),

);

Trong MySQL, CHAR tối đa 255 characters; VARCHAR có giới hạn khai báo tới 65,535 characters nhưng giới hạn thực tế còn phụ thuộc row size và character set.

Thực hành CHAR/VARCHAR

Chọn CHAR hay VARCHAR cho: ISO country code, mã giới tính 1 ký tự, tên khách hàng, email.

Gợi ý

Country code: CHAR(2); mã 1 ký tự: CHAR(1); tên/email: VARCHAR.

9. BINARY và VARBINARY

Hai kiểu này giống CHAR/VARCHAR về ý tưởng fixed/variable length nhưng lưu byte strings, không phải character strings.

file_hash BINARY(32),
token     VARBINARY(255)

BINARY(n)

Độ dài byte cố định.

VARBINARY(n)

Độ dài byte biến đổi.

Đừng nhầm binary data với chuỗi hex hiển thị cho con người. Một hash có thể được lưu dạng bytes hoặc dạng text hex tùy thiết kế.

12. DATETIME vs TIMESTAMP trong MySQL

Cả hai lưu date + time nhưng có semantics/range khác nhau trong MySQL.

Tiêu chíDATETIMETIMESTAMP
Mục đích thường gặpNgày giờ “theo lịch” của sự kiệnTimestamp tạo/cập nhật record
Range MySQLRộng hơnKhoảng 1970–2038 ở MySQL hiện tại
Timezone conversionKhông dùng như TIMESTAMPMySQL chuyển đổi theo session time zone
Default current timeHỗ trợHỗ trợ
 
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
                     ON UPDATE CURRENT_TIMESTAMP,
appointment_at DATETIME
Nếu hệ thống cần lưu ngày giờ ngoài range TIMESTAMP hoặc muốn giữ “wall-clock value” độc lập timezone conversion, DATETIME thường phù hợp hơn.

13. BOOLEAN trong MySQL

Trong MySQL, BOOL và BOOLEAN là synonyms của TINYINT(1). Zero được xem là false; nonzero được xem là true.

CREATE TABLE user_account (
    user_id BIGINT PRIMARY KEY,
    is_active BOOLEAN NOT NULL DEFAULT TRUE
);
Boolean semantics ≠ chỉ lưu đúng 0 hoặc 1 về mặt type. Nếu muốn bắt buộc chỉ 0/1 trong thiết kế cụ thể, có thể thêm CHECK.
is_active BOOLEAN NOT NULL
    CHECK (is_active IN (0,1))

14. ENUM và SET — MySQL-specific

ENUM

Chọn đúng một giá trị trong danh sách.

status ENUM('NEW','PAID','SHIPPED','CANCELLED')
       NOT NULL DEFAULT 'NEW'

SET

Có thể chứa nhiều thành viên từ danh sách định trước.

permissions SET('READ','WRITE','DELETE')
Trade-off: ENUM/SET tiện nhưng gắn schema chặt vào danh sách giá trị. Nếu danh mục thay đổi thường xuyên hoặc có metadata riêng, lookup table + FK thường linh hoạt hơn.

Thực hành ENUM vs Lookup Table

Status đơn hàng có 4 giá trị ổn định; còn danh mục sản phẩm có hàng trăm loại và thay đổi thường xuyên. Cái nào có thể cân nhắc ENUM? Cái nào nên dùng table riêng?

Gợi ý

Order status có thể cân nhắc ENUM; product category nên dùng table CATEGORY + FK.

15. JSON Data Type

MySQL có native JSON type, kiểm tra JSON hợp lệ và cung cấp các JSON functions để truy vấn/chỉnh sửa tài liệu.

CREATE TABLE product (
    product_id BIGINT PRIMARY KEY,
    product_name VARCHAR(150) NOT NULL,
    attributes JSON
);
INSERT INTO product(product_id, product_name, attributes)
VALUES (
  1,
  'Laptop',
  '{"cpu":"i7","ram_gb":16,"ports":["USB-C","HDMI"]}'
);

Khi nào phù hợp?

  • Thuộc tính phụ biến đổi giữa các record.
  • Dữ liệu bán cấu trúc.
  • Không muốn tạo hàng chục nullable columns cho metadata hiếm.
Không dùng JSON để né relational design. Các thuộc tính quan trọng cần constraint, join, index và query thường xuyên vẫn nên là columns/tables rõ ràng.

16. Spatial Data Types

CREATE TABLE warehouse (

17. Character Set và Collation

Data type chuỗi chưa đủ; cần hiểu character set và collation.

Character Set

Cách mã hóa tập ký tự. Với MySQL hiện đại, utf8mb4 là lựa chọn phổ biến cho Unicode đầy đủ.

Collation

Quy tắc so sánh/sắp xếp chuỗi: case sensitivity, accents, locale behavior.

CREATE TABLE person (
    full_name VARCHAR(200)
      CHARACTER SET utf8mb4
);
Hai cột cùng VARCHAR có thể so sánh khác nhau nếu dùng collation khác nhau.

18. Data Type và NULL là hai khái niệm khác nhau

Data type trả lời “giá trị thuộc miền nào?”; NULLability trả lời “có cho phép thiếu/không biết giá trị không?”.

salary DECIMAL(12,2) NOT NULL,
middle_name VARCHAR(100) NULL,
graduation_date DATE NULL
Đừng dùng giá trị giả như 0, 1900-01-01 hoặc '' để thay cho NULL nếu business semantics thực sự là “không biết/chưa có”.

Decision examples

Phone number

INT → VARCHAR. Không tính toán số học; có +, 0 đầu, mã quốc gia.

Money

FLOAT → DECIMAL.

Date of birth

VARCHAR → DATE.

True/False flag

BOOLEAN semantics; hiểu implementation của DBMS.

20. Các lựa chọn sai thường gặp

1. Phone = INT

Mất leading zero, không hỗ trợ '+'.

2. Money = FLOAT

Có sai số floating-point.

3. Date = VARCHAR

Khó validation, sort và date arithmetic.

4. Mọi số = BIGINT

Lãng phí và che mất domain semantics.

5. Mọi text = TEXT

Không thể hiện length expectations rõ.

6. JSON cho mọi thứ

Mất lợi thế schema, constraints và relational query.

7. VARCHAR cho boolean

Dễ phát sinh Yes/Y/TRUE/true/1 lẫn lộn.

8. ID có business meaning nhưng dùng số

Mã như "00123A" nên là string.

22. Ví dụ Schema sử dụng nhiều Data Types

CREATE TABLE customer (
    customer_id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,

    customer_code CHAR(10) NOT NULL UNIQUE,
    full_name VARCHAR(150) NOT NULL,
    email VARCHAR(200) NOT NULL UNIQUE,
    phone VARCHAR(30),

    date_of_birth DATE,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,

    credit_limit DECIMAL(14,2) NOT NULL DEFAULT 0,

    profile JSON,

    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
               ON UPDATE CURRENT_TIMESTAMP,

    note TEXT,

    CONSTRAINT chk_credit_limit
      CHECK (credit_limit >= 0)
);

23. Lab thực hành: Thiết kế Data Types cho E-commerce

Thiết kế bảng PRODUCT với các yêu cầu:

  1. ProductID có thể tăng tới hàng tỷ.
  2. SKU là mã 20 ký tự tối đa.
  3. Tên sản phẩm tối đa 200 ký tự.
  4. Giá tiền chính xác 2 chữ số thập phân.
  5. Stock không âm.
  6. WeightKg là số đo có thể xấp xỉ.
  7. Status chỉ gồm ACTIVE, INACTIVE, DISCONTINUED.
  8. Thông số kỹ thuật linh hoạt.
  9. Ngày tạo tự động.
  10. Mô tả có thể dài.
Xem một lời giải 
CREATE TABLE product (
    product_id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    sku VARCHAR(20) NOT NULL UNIQUE,
    product_name VARCHAR(200) NOT NULL,

    price DECIMAL(14,2) NOT NULL
          CHECK (price >= 0),

    stock INT UNSIGNED NOT NULL DEFAULT 0,

    weight_kg DOUBLE,

    status ENUM(
      'ACTIVE',
      'INACTIVE',
      'DISCONTINUED'
    ) NOT NULL DEFAULT 'ACTIVE',

    specifications JSON,

    created_at TIMESTAMP
      NOT NULL DEFAULT CURRENT_TIMESTAMP,

    description TEXT
);

Thử nghiệm
